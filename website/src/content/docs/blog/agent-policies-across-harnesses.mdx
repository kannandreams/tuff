A coding agent in your repository can run shell commands, read any file it can reach, and call every tool its MCP servers expose. Most of the time that is the point. But every team has a short list of things an agent must never do on its own: force-push to a shared branch, read `.env`, run `terraform apply` without a person looking, or call an MCP tool that deletes things.

Writing that list down is easy. Getting every agent the team uses to actually obey it, and to keep obeying it next month, is the hard part. This post covers why, and how Tuff's policy capability handles it.

## The problem: guardrails live in the wrong places

### Instructions are advice, not enforcement

The first place most teams put a rule is `CLAUDE.md` or `AGENTS.md`: "never force push". The model reads that and usually follows it. Usually is the problem. An instruction file is part of the prompt. It competes with the task, the context window, and whatever the agent decides is the fastest route to a green build. Nothing outside the model checks it.

A guardrail has to sit outside the model, in the harness, where a tool call is matched against a rule before it runs.

### Every harness enforces rules in its own way

Every major harness has a way to do that, and no two use the same one:

The differences go deeper than file names:

- **Different vocabularies.** Some harnesses match rules per tool and per command pattern. Others give you a coarse posture, such as an approval mode and a sandbox level, rather than a list of forbidden commands.
- **Different effects.** One harness can deny, ask, or allow. Another can only allow or deny. A rule that means "ask a person first" may have nowhere to go.
- **Different matching.** A command rule in one harness matches a prefix of the words. In another it is a glob. Paths are relative in one place and absolute in the next.
- **Different homes.** Some rules live in the repository and are reviewed like code. Others live in a user's home directory, where nobody else can see them.

A team running two or three agents ends up with the same intent written several times, in several dialects, by several people. Nobody can say whether the copies agree, and when someone edits one of them while debugging, nobody finds out.

### The failure you do not see

The worst outcome is not a missing rule. It is a rule you *think* is in place. If "deny reading `.env`" is written for a harness that cannot enforce it, or its matching works differently than you expected, the agent reads the file and nobody is told. A guardrail that fails silently is worse than none, because people stop being careful.

## Why one central policy helps

Treat guardrails the way you already treat dependencies: declare them once, in the repository, and generate what each tool needs.

- **One source of truth.** The intent is written once, reviewed in a pull request, and versioned with the code it protects.
- **Shareable.** A platform or security team can publish a policy once, and every project installs the same version instead of copying rules by hand.
- **Honest per harness.** Each harness is asked what it can really enforce, and the answer is stated rather than assumed.
- **Checkable.** Because the generated rules are tracked, drift can be detected and fail CI like any other broken build.

That is what a Tuff policy is.

## How Tuff does it

### Write the policy once

A policy is a capability like a skill or a hook, with its own `tuff.toml`:

```toml title="policies/infra-guardrails/tuff.toml"
id = "infra-guardrails"
type = "policy"
version = "1.0.0"
description = "No force pushes, no secrets, and a human approves terraform apply."

[[policy.rules]]
effect = "deny"
command = ["git", "push", "--force"]
reason = "Force pushes rewrite shared history."

[[policy.rules]]
effect = "deny"
read = [".env", "secrets/**"]

[[policy.rules]]
effect = "ask"
command = ["terraform", "apply"]

[[policy.rules]]
effect = "deny"
mcp = "github:delete_*"
```

Each rule has an effect, `deny` or `ask`, and exactly one subject: a command, file paths the agent must not read, file paths it must not edit, or an MCP tool. The subjects are deliberately small. They are what harnesses can actually match, commands by prefix and paths by pattern, so a rule never says more than it can do. Mistakes are refused when the policy loads, rather than ignored: a rule with two subjects, a `*` inside a command, a path that climbs out with `..`, or a misspelt field.

### Tuff compiles it into each harness's own rules

Tuff does not add a runtime or a proxy between the agent and your machine. It writes the harness's own permission rules, so the harness enforces them the same way it enforces rules you wrote yourself:

Here it is for Claude Code, run in a fresh project:

```sh frame="terminal"
tuff add ./policies/infra-guardrails -a claude
```

```text
Claude: rule 1 (deny command "git push --force") is enforced partially: matches the command as Claude writes it, including inside compound commands; the same program run another way, such as by absolute path, through sh -c, or as git -C . push, is not matched
Claude: rule 2 (deny read ".env", "secrets/**") is enforced partially: covers Claude's file tools and the shell commands Claude Code recognises, such as cat and sed, not a script or program that opens the file itself
Claude: rule 3 (ask command "terraform apply") is enforced partially: matches the command as Claude writes it, including inside compound commands; the same program run another way, such as by absolute path, through sh -c, or as git -C . push, is not matched
installed infra-guardrails (claude) -> .claude/policies/infra-guardrails/policy.toml
compiled 5 permission rule(s) for infra-guardrails (claude) -> .claude/settings.json
```

Four rules became five native rules, because the `read` rule lists two paths:

```json title=".claude/settings.json"
{
  "permissions": {
    "ask": [
      "Bash(terraform apply *)"
    ],
    "deny": [
      "Bash(git push --force *)",
      "Read(/**/.env)",
      "Read(/secrets/**)",
      "mcp__github__delete_*"
    ]
  }
}
```

Notice what came first: a caveat for every rule that is only partly enforced. You learn at install time that `sh -c "git push --force"` would get past the command rule, not after an incident. The [policies reference](/primitives/policies/) has a short recording of this policy stopping Claude Code from reading `.env`.

### A harness that cannot enforce the policy is refused

Tuff compiles policies for Claude Code today. Asking for another harness does not quietly write a file that harness ignores. It stops, installs nothing, and lists every rule that would not be enforced:

```sh frame="terminal"
tuff add ./policies/infra-guardrails -a cursor
```

```text
error: policy 'infra-guardrails' would not be enforced as written, so it was not installed:
  Cursor: rule 1 (deny command "git push --force") is not enforced: Tuff does not compile policy rules for this agent yet
  Cursor: rule 2 (deny read ".env", "secrets/**") is not enforced: Tuff does not compile policy rules for this agent yet
  Cursor: rule 3 (ask command "terraform apply") is not enforced: Tuff does not compile policy rules for this agent yet
  Cursor: rule 4 (deny mcp "github:delete_*") is not enforced: Tuff does not compile policy rules for this agent yet
hint: run 'tuff policy matrix' to see what each agent can enforce
```

This is the silent gap from earlier, closed on purpose. `tuff policy matrix` prints every harness, effect, and subject with a coverage of `full`, `partial`, or `unsupported`, the same terms the [Hooks Specification](/spec/hooks/) uses, so the claim is written down and reviewable rather than implied.

### A policy cannot allow anything

There is no `allow` effect, and a rule that uses one is refused. A policy is meant to be shared: it can come from another team's repository or a published pack. A shared policy that could grant permissions could quietly widen what an agent may do in every project that installs it. A policy that can only take permissions away can, at worst, be too strict, and too strict is something you notice straight away. Permissions an agent *should* have stay in the harness's own settings, owned by the project.

## Keeping the guardrails in place

Installing the rules is day one. Guardrails usually fail later, when someone deletes a line while debugging a denied command and forgets to put it back. Tuff treats the compiled rules as managed output.

### Your settings file stays yours

Tuff adds its rules next to whatever is already in `.claude/settings.json` and records each one it wrote in `tuff.lock`. It never rewrites rules it did not add, a rule already present is not added twice, and a settings file that is not valid JSON is left alone and stops the install before anything is written.

### Drift fails the check

Remove `Read(/**/.env)` from the settings file by hand, then run:

```sh frame="terminal"
tuff check
```

```text
✗ infra-guardrails         policy claude       modified (.claude/settings.json#permissions.deny)
```

`tuff check` exits non-zero, so the same command that guards your skills and hooks in CI now guards your guardrails. The [CI guide](/cli/ci/#ci-with-github-actions) shows the GitHub Actions setup. To put the rules back:

```sh frame="terminal"
tuff update infra-guardrails -a claude --force
tuff check
```

```text
compiled 5 permission rule(s) for infra-guardrails (claude) -> .claude/settings.json
✓ infra-guardrails         policy claude       ok
```

### Updates and removal touch only what the policy owns

When the platform team ships `infra-guardrails` 1.1.0 without a rule, `tuff update` removes the rule the new version dropped. `tuff delete` removes exactly the rules the policy added and nothing else. In a settings file that also held a hand-written `Bash(curl *)` deny rule and a `model` setting, deleting the policy leaves this:

```json title=".claude/settings.json"
{
  "model": "opus",
  "permissions": {
    "deny": [
      "Bash(curl *)"
    ]
  }
}
```

## Where policies sit among your defences

A policy is one layer, and it helps to be clear about which one:

| Layer | Example | What it stops |
|---|---|---|
| Instructions | `CLAUDE.md`, `AGENTS.md` | Nothing on its own. The model reads it as advice. |
| Harness policy | A Tuff policy compiled to permission rules | The agent's own tool calls that match a rule, before they run. |
| Sandbox | The harness's operating-system sandbox, containers | The action at the operating-system level, however it is written. |

Harness permission rules match the tool call the agent makes, which is why Tuff reports command and file rules as `partial`. Claude Code's own documentation says these rules are not a security boundary. Policies are very good at stopping the accidents that actually happen, such as a force push or a stray read of `.env`. When something must never be reached, also turn on the harness's sandbox. Tuff cannot turn it on for you, because no file in the repository controls it.
